# NDR Resolution System

Classifies free-text WhatsApp replies to failed-delivery (NDR) notifications into
delivery-failure intents, and maps each intent to an operational action.

Runs on CPU, no GPU, no external API. Roughly 0.5 ms per message.

```bash
python train.py                    # build corpus, train, evaluate, save model
python eval_challenge.py           # honest out-of-distribution evaluation
python predict.py --demo
python predict.py --text "kl subhh 11 bje bhejna ghr pe koi ni h"
python predict.py --csv replies.csv --out resolved.csv
```

## 1. Results, stated honestly

| Evaluation | Accuracy | Macro F1 |
|---|---|---|
| Held-out split of the synthetic corpus | **99.7%** | 0.997 |
| 5-fold CV on the synthetic corpus | — | 0.997 ± 0.001 |
| **Hand-written out-of-distribution set (n=64)** | **62.5%** | **0.626** |

**Do not quote the 99.7%.** The held-out split is generated by the same templates
as the training data, so it measures memorisation of the generator. The 62.5% on
unseen phrasings is the number that carries information.

The gap between those two rows is the single most important fact about this
project, and any version of it that reports only the first number is misleading.

### What 62.5% actually costs

Flat accuracy is the wrong metric here, because "escalated to a human" is a
*correct* outcome, not an error. Scoring by what the system would actually do:

| Mode | Volume | Correct | Cost of an error |
|---|---|---|---|
| `AUTO_EXECUTE` | 43.8% | 92.9% | wrong action, no human in the loop |
| `REVIEW` | 21.9% | 28.6% | caught by a reviewer |
| `HUMAN_REQUIRED` | 34.4% | 45.5% | none — a human decides |

**2 of 64 replies (3.1%) would receive a wrong action with nobody watching.**
Every other error lands in a queue before anything happens. The abstention layer
is what converts a mediocre 62.5% classifier into a system that automates ~44%
of NDRs at 93% precision.

The two silent failures are both vocabulary gaps, not reasoning failures:

- `"street name is not correct in the label"` → CUSTOMER_UNAVAILABLE @ 0.90
- `"utne rupay ghar me nahi the"` → CUSTOMER_UNAVAILABLE @ 0.97

Neither "street name" nor "rupay" appears anywhere in the training templates, and
the model is badly over-confident on both. Fixing over-confidence is more urgent
than fixing accuracy — see §5.

## 2. Architecture

```
WhatsApp reply
      │
      ▼
┌─────────────────────┐   Devanagari→Roman · emoji strip · elongation collapse
│  normalize.py       │   ~400-entry Hinglish variant lexicon · entity masking
└─────────────────────┘
      │  normalized text + {date, time, phone, pincode}
      ▼
┌─────────────────────┐   TF-IDF word 1-2 grams  ⊕  char_wb 2-5 grams
│  model.py           │   → multinomial logistic regression (13 classes)
└─────────────────────┘
      │  intent + probability distribution
      ▼
┌─────────────────────┐   high-precision regex guardrails
│  rules.py           │   agree → boost · disagree → cap confidence → review
└─────────────────────┘
      │
      ▼
┌─────────────────────┐   confidence thresholds · entity-conditioned refinement
│  taxonomy.py        │   irreversible-action gating
└─────────────────────┘
      │
      ▼
   action + mode (AUTO_EXECUTE / REVIEW / HUMAN_REQUIRED) + reason
```

### Why character n-grams, not a transformer

Character 2-5 grams are doing most of the work. `dlvry`, `delivry`, `dilivery`
and `delivary` share almost no word features but share the trigrams `liv`, `lvr`,
`vry`. Ablation on the OOD set:

| Features | OOD accuracy |
|---|---|
| word 1-2 grams only | 0.656 |
| char 2-5 grams only | 0.625 |
| **word + char** | **0.703** |
| word + char, *no normalization* | 0.625 |

(These are pipeline-only numbers, before the decision layer.) Normalization is
worth ~8 points on its own — the lexicon is not decoration.

A transformer is the obvious next step, but not the obvious *first* step:
pretrained subword vocabularies assume well-formed text, most Indic models are
not trained on romanized Hindi, and this pipeline classifies a message in well
under a millisecond with no inference bill at NDR volume. Beat this baseline
before paying for one.

### Why intent and action are separate

Business policy changes more often than language does. When ops decides that
`OUT_OF_STATION` should hold at hub rather than reschedule, that is a one-line
edit in `taxonomy.py` and no retraining. Several intents also collapse onto the
same action (`REFUSED_NOT_NEEDED` and `CANCEL_REQUEST` both end in RTO);
predicting the action directly would throw away the signal that separates them
and make failures much harder to debug.

## 3. Two design decisions that matter operationally

**`FAKE_ATTEMPT_DISPUTE` is its own class.** In Indian last-mile, a meaningful
share of NDRs are marked without an attempt ever being made. Folding those into
"customer unavailable" auto-reschedules them, hides a 3PL quality problem, and
inflates RTO. Isolating the class routes it to a partner dispute instead. This
class also needs word order, not just word presence: *"koi nahi **tha**"* (nobody
was home — customer's fault) and *"koi nahi **aaya**"* (nobody came — courier's
fault) share nearly every token and demand opposite actions. That pair is exactly
what the regex layer exists for.

**Irreversible actions are gated on a human regardless of confidence.** `CANCEL_ORDER`
and `INITIATE_RTO` destroy a sale and cannot be undone. `REQUIRES_HUMAN_APPROVAL`
in `taxonomy.py` blocks them at 0.99 confidence. On the OOD set no irreversible
action was ever wrongly auto-executed — by construction, not by luck.

## 4. A bug worth recording

The first version of the `ALREADY_RECEIVED` rule was `\b(milla|already)\b`. It
fired on *"market se sasta mil gaya"* — "I found it cheaper elsewhere", which is
`REFUSED_NOT_NEEDED`. The rule was therefore **suppressing RTO on parcels the
customer had explicitly rejected**, the most expensive possible error.

Auditing the rule layer in isolation also showed it fired on only 3 of 64 OOD
messages. It is a guardrail, not a classifier, and it should not be mistaken for
one. Any hand-written rule layer needs its own precision measurement — the
intuition that a rule is "obviously right" is not evidence.

## 5. What to do next, in priority order

1. **Replace the synthetic corpus with real labels.** Sample 3–5k replies from
   the WhatsApp BSP logs, have ops label them against this taxonomy, measure
   inter-annotator agreement. Every number above is a smoke test until this
   exists. Nothing else on this list matters as much.
2. **Fix calibration before accuracy.** The damaging errors are wrong *and*
   confident (0.90, 0.97). `CalibratedClassifierCV` with isotonic regression, plus
   per-class thresholds tuned on real data, will convert silent failures into
   escalations without improving the classifier at all.
3. **Active learning loop.** Everything routed to `REVIEW`/`HUMAN_REQUIRED` is
   already being labelled by ops. Feed it back weekly. Low-confidence examples are
   exactly the highest-value training data.
4. **Multi-intent handling.** *"address change karo aur kal bhejna"* carries two
   actions; the model currently returns one and the runner-up probability is the
   only hint. A multi-label head is the correct fix.
5. **Monitoring.** Track intent distribution drift, `AUTO_EXECUTE` share, and
   reviewer override rate per intent. A sudden rise in `UNCLEAR` usually means
   the WhatsApp template changed, not that customers changed.
6. **Close the loop on outcomes.** The real target metric is not classification
   accuracy — it is second-attempt success rate and RTO percentage. Log the
   action taken and join it to the eventual delivery outcome, so the system can
   eventually be trained on what actually worked rather than on what a customer
   appeared to intend.

## 6. Files

| File | Purpose |
|---|---|
| `ndr/taxonomy.py` | 13 intents, 11 actions, thresholds, decision policy |
| `ndr/normalize.py` | Hinglish normalization + entity extraction |
| `ndr/data.py` | synthetic corpus generator + noise model |
| `ndr/rules.py` | high-precision regex guardrails |
| `ndr/model.py` | features, classifier, rule fusion, `NDRResolver` |
| `train.py` | training + in-distribution evaluation |
| `eval_challenge.py` | out-of-distribution evaluation (the honest one) |
| `predict.py` | CLI: single message, batch CSV, demo |

Train on your own labels with `python train.py --csv labelled.csv`
(columns: `text`, `intent`).
